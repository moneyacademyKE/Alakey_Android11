**M52 detail.** Call chain: AlakeyUI.kt:283 (folder-header action) → AppViewModel.kt:331 → UniversalRepository.kt:37 `unsubscribe(title) = dao.deleteByTitle(title)` → PodcastDao.kt:33-34 `DELETE FROM podcasts WHERE title = :title`. Nothing touches `facts`. `compact()` (FactDao.kt:35-41) keeps the latest tx per (entityId, attribute) — it bounds rows *per entity*, never the entity set. So fact history grows with **lifetime subscriptions, not the current library**, and M43's `SELECT * FROM facts` (FactDao.kt:25-26, no WHERE / no LIMIT) loads all of it into JVM heap at 5 production hydrateAll sites (PlaybackStateRepository.kt:33,:52,:60,:65 + DownloadRepository.kt:33 + UniversalRepository.kt:36). This is M12's exact disease — "event_log grows unbounded, no retention sweep" — on the table that actually holds user state, fixed there (`purgeOlderThan`, EventLog.kt:25-26) and unfixed here. Fix: delete facts for the removed ids inside `unsubscribe` (one `@Query("DELETE FROM facts WHERE entityId IN (:ids)")` + resolve the ids before `deleteByTitle`), or a retention sweep mirroring M12's. Dedupe: `grep -ciE "unsubscribe|deleteByTitle" LEDGER` = **0** → new. Conf: mechanism h, runtime impact m (no emulator per M25).

**M53 detail.** :82 `runCatching { dbFile.copyTo(backup, overwrite = true) }` handles its result and logs both branches; :86 `dbFile.delete()` and :87-89 (`-wal`/`-shm`/`-journal`) discard theirs and proceed unconditionally. If the v12 file survives, Room opens it, finds no migration to 14, and throws on every launch — escapable only by clearing app data. KDoc :69-70 reasons about the *copy* failing ("a bricked launch is worse than a logged loss"); the delete-failure branch produces exactly the bricked launch it rejects, so the comment and the code disagree. Fix: check the Boolean and, on failure, rename the file aside (`alakey-db.unremovable-<ts>`) so Room builds fresh, plus `Log.e`. Severity is impact-weighted per this ledger's convention (M22 latent = medium); trigger probability is LOW — an app can normally always delete its own database file, and :75's READONLY handle is closed by `.use`. Conf: mechanism h, trigger unverified.

**L52 detail.** Why dead code earns a finding here: PodcastDao's only other write is :36 `UPDATE podcasts SET palette`, so *nothing today* can rewrite a row's `audioUrl` — and that is precisely what keeps Migrations.kt:34's proof guard sound, because InformationModel.kt:38 hydrates `audioUrl` into a **local file path** for downloaded episodes. Wire `savePodcast` up with a hydrated entity (the natural argument for a method with that name; AppViewModel passes hydrated entities everywhere, e.g. :349 `markPlayed`) and the persisted audioUrl becomes `/data/user/0/.../<sha>.mp3`. Two consequences: the migration silently skips that row (guard fails → id stays legacy → the next sync derives a fresh id → **duplicate episode**, M14's failure mode reborn), and DownloadRepository.kt:47 `Request.Builder().url(podcast.audioUrl)` throws on a non-http URL inside NetworkCall's 3-attempt retry (L20). Loaded gun, no trigger. Fix: delete UniversalRepository.kt:34 + PodcastDao.kt:27-28, or take explicit fields instead of an entity. Conf h (grep), hazard latent.

**L53 detail.** After an upgrade, `grepLogs` / `getEventsByType` (EventLog.kt:31-39) return rows whose payload id no longer resolves via `getPodcastById` — and those queries plus `rawQuery` are the entire on-device inspection surface the README still advertises (M32/L45). Cheapest honest fix is documentation: Migrations.kt:12-15 says "both tables that reference them are rewritten" — event_log is a third table that references them. Conf h.

## NOT FILED (checked, clean — do not re-investigate)
- `EpisodeIds.isLegacyHashId` (:30-31) accepts **Unicode** decimal digits — `Char.isDigit()` delegates to `Character.isDigit(char)`, true for e.g. U+0660 — so a non-ASCII numeric id passes the shape test. Harmless: the :34 proof guard compares against `Int.hashCode().toString()`, always ASCII, so such a row is skipped. Defense in depth does its job.
- The `UPDATE facts SET entityId` rewrite cannot violate a constraint: 14.json `createSql` = `PRIMARY KEY(entityId, attribute, tx)` with 3 non-unique indices, and a derived id is always 16 hex chars while every pre-migration id is ≤11 digits or contains `/` → no newId can pre-exist.
- No foreign keys anywhere (14.json: `fks=0` on podcasts, event_log, facts) → rewriting a PK column carries no cascade or enforcement risk.
- `db.query(…).use {}` closes the cursor; the two `compileStatement` programs (:40-41) are never closed — bounded at 2 per migration on a connection-scoped handle, not worth an ID.
- `legacyDecision(version = null) → PassThrough` on a corrupt/unreadable DB means Room throws on open rather than rebuilding. Documented (:23-24 "never wipe on a read failure") and unit-tested (LegacyDecisionTest:23-25) — a deliberate trade, not a defect.
- `preserveLegacyDatabase` opens the DB READONLY *before* checking `dbFile.exists()`; on a fresh install `openDatabase` throws, `runCatching` swallows it to null, and `legacyDecision(false, null, 13)` → `Absent`. Correct, if slightly backwards in reading order.
