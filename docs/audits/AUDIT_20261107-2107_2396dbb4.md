### M73 — `ORDER BY pubDate DESC` does not order by date

`PodcastDao.kt:15` is `@Query("SELECT * FROM podcasts ORDER BY pubDate DESC")`. `pubDate` is TEXT with SQLite's default BINARY collation — `14.json:21` reads `` `pubDate` TEXT NOT NULL `` and `COLLATE` has 0 hits in the schema. The stored value is the **raw feed string**: `RssParser.kt:65` `pubDate = entry.directText("pubDate", "published")`, no normalization. The repo's own fixtures prove two formats live in that one column — `RssParserTest.kt:25` `Mon, 01 Jan 2024 10:00:00 +0000` (RFC-822) and `RssParserTest.kt:53`/`:65` `2024-01-01T10:00:00Z` (ISO-8601). Lexicographic DESC on RFC-822 therefore sorts on the weekday abbreviation, and because ASCII digits sort below letters, every ISO episode lands below every RFC-822 episode regardless of when it aired.

`sqlite3 :memory:` probe this shift (6 rows, 1–5 Jan 2024 plus one ISO 4 Jan):

    actual   ORDER BY pubDate DESC: jan3-wed, jan2-tue, jan4-thu, jan1-mon, jan5-fri, jan4-iso
    correct  newest-first:          jan5-fri, jan4-thu / jan4-iso, jan3-wed, jan2-tue, jan1-mon

The newest RFC-822 episode sorts 5th of 6; the ISO episode sorts last.

Consumers: `UniversalRepository.kt:21` (library), `:22` (queue), `:25` (inbox), `PlaybackStateRepository.kt:33/:60/:65`, `DownloadRepository.kt:33`. `LibraryFilters.kt:14,17,18` re-sorts all three UI branches through `PureLogic.parseDate`, which **masks** the defect in the library view — it does not mask it for (a) `maxByOrNull { parseDate(it.pubDate) }` at `PureLogic.kt:21`/`:26`, whose tie-break on equal-or-unparsable dates is list order (in M56's all-zero Atom case this SQL order *is* the answer that decides what gets auto-downloaded), (b) `PodcastDao.kt:30-31` `getEpisodesByTitle`, which carries no `ORDER BY` of its own and inherits table order, and (c) every non-UI consumer above.

Hickey: one question ("which episode is newest") answered twice by two mechanisms that disagree — a text sort in SQL, a parsed sort in the UI. Fix = normalize once at the boundary (persist an epoch-millis or ISO-8601 column, sort in SQL, delete the three Kotlin re-sorts). Rejected alternative: add a fourth sort or a `COLLATE NOCASE` — that keeps two answers. Conf h (probe + fixtures + schema); user-visible ordering not device-verified (M25).

### M74 — subscription identity is a display string

`PodcastDao.kt:33-34` `DELETE FROM podcasts WHERE title = :title` and `:30-31` `SELECT * FROM podcasts WHERE title = :title` key episode identity on `title`, which is the **channel** display name copied onto every row (`RssParser.kt:58` `title = channelTitle`). Callers: `UniversalRepository.kt:37` `unsubscribe(title)` ← `AppViewModel.kt:331` ← `AlakeyUI.kt:283` (the folder header the user taps); `UniversalRepository.kt:36` `getPodcastsByTitle`; `PlaybackStateRepository.kt:52` resolves resume via `getEpisodesByTitle(ref.title)`.

Two reachable consequences, and the first needs only one feed:

1. **A publisher renames the channel** → new episodes persist under the new title while existing rows keep the old one → one show renders as two folders, and `deleteByTitle` can only ever remove one of them, so the other survives an unsubscribe permanently.
2. **Two subscribed feeds share a `<title>`** (syndicated mirrors, or generic names like "News") → they are indistinguishable, so unsubscribing one deletes both.

The natural key already exists and is already used for sync: `PodcastDao.kt:21-22` `SELECT DISTINCT feedUrl FROM podcasts WHERE feedUrl != ''`, with `feedUrl` a persisted column (`PodcastEntity.kt:24`). `PodcastEntity`'s own KDoc claims "one name, one meaning … the DB cannot lie about them" while the repository identifies rows by what they display.

**Note for PR #78 before merge:** round-3's M52 fix (`getIdsByTitle → deleteByTitle → deleteByEntityIds`, ROUND-3-STATUS) builds on the title key, so it inherits this — resolving fact ids from a title widens consequence 2 from episodes to user state. Fix: key subscription on `feedUrl`, keep `title` for display. Dedupe: `deleteByTitle|unsubscribe|same title` over the ledger hits only M52 / M52-SHARPEN / RICH-HICKEY-1607, all about fact retention — 0 hits on title-as-identity. Conf h.
