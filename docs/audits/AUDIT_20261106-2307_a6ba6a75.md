### M47 — palette extraction is dead, so every themed surface renders hardcoded cyan/grey

`AppViewModel.kt:147`:

```kotlin
if (podcast != null && podcast.imageUrl != _uiState.value.current?.imageUrl) extractColor(podcast.imageUrl)
```

The line immediately above (`:136-146`) is `updateState { state -> state.copy(current = podcast ?: state.current, …) }`. `MutableStateFlow.update` is a synchronous CAS loop and there is **no suspension point between `:146` and `:147`**, so `_uiState.value.current` at `:147` is already `podcast` — the two `imageUrl` values compared are the same string. The condition is false on every episode change, and `git grep -n extractColor a6ba6a75 -- '*.kt'` returns exactly two hits: this call site and the declaration at `:372`. Nothing else calls it.

Downstream, all of this is therefore dead in production:

- `_uiState` colour fields keep their construction defaults (`AppViewModel.kt:57-59` `AndroidColor.CYAN / CYAN / GRAY`; `UISpecs.kt:47-49` `0xFF00FFFF / 0xFF00FFFF / 0xFF808080`).
- `repo.savePalette(podcast.id, palette)` (`:378`) never runs → `PodcastEntity.palette` is never populated → `UniversalRepository.kt:47 savePalette` and `ui/PaletteExtractor.kt` (a Hilt `@Inject` class) have no live caller.
- The surfaces that consume those colours: `AlakeyUI.kt:122` `FluxBackground(color = Color(state.dominantColor))`, `PlayerComponents.kt:140` `FluxBackground(spec.dominantColor)`, `:102` mini-player progress tint, `:192` scrubber, `:244` queue-row highlight, `:305` slider active track. The "prismatic glass" identity the docs advertise renders in one constant cyan regardless of artwork.

**Honest calibration.** The guard is not unreachable *by construction*: the library collector (`:121-128`) can replace `current` with a different instance for the same id (`library.find { it.id == old.id } ?: old`), so an artwork change landing between the two collectors would satisfy the inequality. The defect is that it never fires on the event it was written for — a media-item change. Not verified on a device (no emulator job per M25): confidence **h** on the code path, **m** on the runtime observation.

**Cheapest fix (one line):** capture the previous value before the write — `val previousImageUrl = _uiState.value.current?.imageUrl` above `:136`, then compare `podcast.imageUrl != previousImageUrl`. The repo already proves the better shape with the `chaptersLoadedFor` memo (`:113`, set at `:240`, gated at `:148`): a `paletteLoadedFor` memo is the same pattern and cannot be invalidated by its own write.

### L46 — history nobody reads, written from inside a retry loop

`AppViewModel.kt:109-110` declares `_history = mutableStateListOf<UiState>()` plus a public `history` getter; tree-wide grep finds **four** hits, all inside this file (decl, getter, `add` at `:256`, trim at `:257`) — no reader in `app/src/main`, `wear/src`, or either test source set.

`updateState` (`:252-261`) mutates that Compose snapshot list **inside** `_uiState.update { … }`. `update` re-invokes the lambda when the CAS loses a race, so the side effect can run twice for one logical state change (duplicate entry, or a double `removeAt(0)`). It is invoked from the playback-projection collector (`:133-146`), i.e. on every position tick.

Cost, calibrated: `state.copy(podcasts = library)` shares the same `List` instance across snapshots, so retention is roughly the number of *distinct* library lists, not 50× the library — this is a hygiene and correctness defect, not a memory leak. Deleting `:109-110` and `:255-258` reduces `updateState` to `_uiState.update(transform)`: less code, same behaviour for every actual consumer.

### L47 — a failed chapters fetch is cached as "this feed has no chapters", forever

`loadChapters` sets the memo **before** the fetch (`:240 chaptersLoadedFor = podcast.id`), and the gate that would retry is `:148 playback.currentMediaId != chaptersLoadedFor` — so re-selecting the same episode never re-attempts. The fetch result is cached unconditionally at `:247 chaptersCache.getOrPut(url) { repo.fetchChapters(url) }`, and `FeedRepository.fetchChapters:57-66` returns `emptyList()` both for a non-2xx response and for any exception (`runCatching { … }.getOrDefault(emptyList())`). One 502 or one dropped socket on a train pins zero chapters for that URL for the life of the process, indistinguishable in the UI from a feed that genuinely ships none.

Fix: cache only non-empty results and move `:240` after a successful fetch — two small edits, no new abstraction. (`chaptersCache` itself is unbounded per process; bounded by distinct episodes played, so not filed.)

### L48 — the reconnect hook that does nothing, sitting on top of a poisoned singleton

`AlakeyUI.kt:88` calls `vm.connect()` inside `LaunchedEffect(Unit)`; `AppViewModel.kt:264` is `fun connect() = Unit`. It reads as "re-attach the player when the UI comes back" and is inert.

That matters because of H5 (already filed, not re-filed): `AppViewModel.onCleared` (`:383-384`) calls `playbackClient.cleanup()` on a `@Singleton` (verified `PlaybackClient.kt:38`), `cleanup()` sets `cleanedUp = true` (`:412-413`) and never resets it, `scheduleReconnect` returns early on that flag (`:139`), and the controller's `onDisconnected` listener returns early on it too (`:106`). So once an activity is cleared during playback there is no path back to a live controller — and the one UI call shaped like that path is a no-op. H5's fix surface should either delete `connect()` from both files (stop advertising a capability that does not exist) or make it real (`if (cleanedUp) { cleanedUp = false; connect() }` plus cancelling/replacing `scope`).

Also noted, no impact, not filed separately: `cycleTimer`'s `0 -> playbackClient.cancelSleepTimer()` branch (`:234`) is unreachable — the `when` at `:223-230` can only yield `null`, 15, 30, 45, 60 or `-1`.
