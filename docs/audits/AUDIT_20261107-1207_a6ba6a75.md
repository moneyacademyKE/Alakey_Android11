### M68 — the wall clock is doing a monotonic clock's job

Census, `git grep` at `a6ba6a75`, scope `app/src/main wear/src/main tile-contract/src`:

- `System.currentTimeMillis()` → **11 hits in 6 files**
- `SystemClock` / `elapsedRealtime()` / `nanoTime()` / `uptimeMillis()` → **0 hits**
- Same two greps at PR #76 head `e1576f7` → **11 and 0**. The fix branch does not change this.

Seven of the eleven sites are *timestamps* (a date that gets stored or sent) and are correct
on the wall clock. **Four compute an elapsed interval**, where a wall-clock step is a bug:

1. **WearBridge.kt:49 / :52 / :55** — watch tile tick pacing.
   `:52 val dueTick = np.isPlaying && System.currentTimeMillis() - lastPushMs >= TICK_MS`
   (`TICK_MS = 15_000L` at `:23`), with `:55 lastPushMs = np.timestampMs`.
   A backward clock step of N ms makes the difference negative for N ms, so `dueTick` is
   false for that whole window → **no periodic push at all while audio keeps playing** → the
   watch tile freezes on a stale position. This is a second, independent cause of M9's
   "stale frame renders as live forever": M9 fixed the `timestampMs == 0L` sentinel, this one
   survives that fix. PR #76 rewrites this file (+74/-27: node gate, `IDLE_POLL_MS`) and the
   wall-clock tick is still there at `:70` (`now - lastPushMs >= TICK_MS`).

2. **AppViewModel.kt:149-153** — progress-save throttle.
   `:150 playingSave = playback.isPlaying && now - lastSaveMs >= PROGRESS_SAVE_INTERVAL_MS`
   (5_000L, `:389`), `:151 pauseSave = wasPlaying && !playback.isPlaying && now - lastSaveMs
   >= PROGRESS_SAVE_MIN_GAP_MS` (2_000L, `:390`).
   Backward step → both false → **no progress writes until the clock climbs back past the old
   `lastSaveMs`**; a crash or a kill in that window loses the resume position, and
   `:155 updateLastPlayed` stops with it, so the "Continue" filter's ordering goes stale too.
   Forward step → the throttle collapses and every poll tick writes two facts.

3. **PlaybackClient.kt:164 + :326** — smart-resume rewind gate.
   `:164 if (!isPlaying) lastPauseTime = System.currentTimeMillis()`,
   `:326 if (lastPauseTime > 0 && (System.currentTimeMillis() - lastPauseTime) >
   RESUME_REWIND_AFTER_MS)` (5 min, `:427`).
   A forward step larger than the threshold while paused → an **unrequested rewind** the user
   never asked for; a backward step → smart resume never fires, for any pause length.

4. **AlakeyUI.kt:434-438** (`MotionDetector`, class at `:426`, `lastUpdate = 0L` at `:427`) —
   shake rate math. `:435 if (now - lastUpdate > 100)` guards `:436 val diff = now - lastUpdate`,
   which divides at `:438`. A backward step makes the guard false for the step's magnitude →
   **shake-to-extend silently stops working** and comes back only when the clock catches up.
   Same silence family as L19, different cause: L19 is "no accelerometer", this is "clock moved".

Fix (Hickey): the complection is that one call — `currentTimeMillis()` — is being asked to mean
two different things, "what time is it" and "how long has passed". Separate them: a 3-line
`object Monotonic { fun now() = SystemClock.elapsedRealtime() }`, swap the **4 interval sites**,
and leave the **7 timestamp sites alone** (`FactEntity.kt:19` tx, `FeedRepository.kt:44` event
timestamp, `PlaybackStateRepository.kt:20`/`:24` lastPlayed, `WearBridge.kt:49` as a wire value) —
those are dates, and `elapsedRealtime()` is meaningless across a reboot. Do not "fix" all 11.

Conf: mechanism **h** (the arithmetic is on the page). Trigger frequency **l-m** — a wall-clock
step is rare but routine: NTP resync after flight mode, a manual date change, a carrier time
update. Nothing in CI can catch it (M25: no emulator job; M27: no virtual-time harness).

### M69 — the queue is a sequence being stored as a date

`PlaybackStateRepository.kt` in full (68 LOC), all four defects in one idiom:

- `:29 factStore.assert(id, InformationModel.ATTR_QUEUE_ORDER, System.currentTimeMillis().toString())`
- `:35 .sortedBy { it.queueOrder }` → `:36 val firstOrder = queue.firstOrNull()?.queueOrder ?: System.currentTimeMillis()` → `:38 (firstOrder - 1)`

1. **Same-millisecond ties.** Two episodes queued inside one millisecond get *identical*
   `queueOrder`; `sortedBy` is stable, so the tie resolves by input order, which is whatever the
   caller happened to pass. Batch queue adds are exactly the case that lands in one ms. The same
   sort runs at two more sites — `UniversalRepository.kt:23` and `AppViewModel.kt:123` — so the
   ambiguity is rendered in two places, not one.
2. **A clock step reorders the user's explicit choice.** Because append stamps a wall-clock
   millis and "play next" computes `min - 1`, a backward step makes a freshly `addToQueue`'d
   episode's order *smaller* than items already queued next → it jumps ahead of them. The user
   said "play this next" and the queue disagrees.
3. **Empty-queue seed is a timestamp.** `:36` falls back to `System.currentTimeMillis()` rather
   than `0`, so the ordinal space is anchored to ~1.7e12 and `firstOrder - 1` decrements that
   base forever. Harmless today (one element), wrong by construction.
4. **Clock-independent path to the same bug.** `queueOrder` is `Long = 0` (`PodcastEntity.kt:40`,
   an `@Ignore var` outside the data-class constructor per M55) and hydrates via
   `InformationModel.kt:36 fact.value.toLongOrNull() ?: queueOrder`. A malformed or truncated
   fact yields **0**, which sorts *first* — ahead of every real queue entry. No clock needed.

Fix (Hickey): a queue position is data, not a time. `maxOf(existing) + 1` to append, `minOf(existing) - 1`
(or insert-at-index then renumber) for "play next", `0` as the empty seed. Three pure functions,
zero clock reads, and the tie case disappears because the values are distinct by construction.
Conf **h** — all four paths read directly off the source, no inference.

### L69 — the sleep timer is a loop counter wearing a clock's clothes

`PlaybackClient.kt:375-381`, verbatim:

```
sleepTimerJob = scope.launch {
    while (_sleepTimerSeconds.value > 0) {
        delay(1000)
        _sleepTimerSeconds.value--
    }
    _sleepTimerTotalSeconds.value = 0
    pause()
}
```

- **It can only run late.** 3600 iterations for a 60-minute timer, each `delay(1000)` plus
  dispatch overhead, and nothing ever reconciles against a deadline. The drift is small but
  structurally one-directional, and it is *unbounded* in the overhead direction.
- **No wake machinery anywhere.** `git grep -nE "AlarmManager|WakeLock|setWakeMode" a6ba6a75 --
  app/src wear/src` = **0 hits**. kotlinx `delay` is monotonic-based and Android's
  `CLOCK_MONOTONIC` does not advance in deep sleep, so the one feature whose entire job is to
  stop audio after the user falls asleep is the timer that stops counting when the device sleeps.
  **Honest caveat — conf m, not h:** active media playback normally keeps the CPU awake through
  the audio HAL, and the app also holds a `mediaPlayback` FGS (M15), so I cannot assert the
  timer stalls during real playback without a device, and M25 means CI never will. The
  unambiguous half is the drift: remaining time is not derived from a deadline, so it can never
  be corrected.
- **Secondary, same 6 lines:** `:378 _sleepTimerSeconds.value--` is a non-atomic
  read-modify-write on a `MutableStateFlow` (declared `:78`), while `resetSleepTimer()` writes
  `_sleepTimerSeconds.value = initialSleepDuration` from the UI thread. Interleave them and the
  reset is lost. The repo already knows the correct shape — `_desiredState.update { ... }` is
  used throughout this same file.

Fix: store `deadlineMs = Monotonic.now() + minutes * 60_000L` and compute remaining from it each
tick — one value, self-correcting, honest display, and M68's helper is exactly what it needs.

## Rich Hickey pass

- **The time surface is 11 call sites and 2 idioms.** That is a small, closed, fixable surface —
  not a systemic problem. The complection is a single overloaded call: `currentTimeMillis()`
  means "what time is it" in 7 places and "how long has passed" in 4. Naming the second one
  (`Monotonic.now()`) dissolves the whole class of bug in ~10 changed lines.

  It buys nothing (nothing displays `queueOrder` as a time) and costs ordering correctness.

  data; the loop counter is the incidental complexity.
