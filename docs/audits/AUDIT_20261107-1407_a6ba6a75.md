### H10 — the latch outlives its owner

`WearBridge` is a Kotlin `object` (`:21`), i.e. process-global, holding `@Volatile private var started = false` (`:25-26`). `start()` guards with `if (started) return` (`:29`), latches at `:35`, then launches the poll loop into **the caller's scope**: `scope.launch(Dispatchers.Default) { while (true) { … delay(POLL_MS) } }` (`:37-59`). The only caller is `ui/AppViewModel.kt:163` `WearBridge.start(context, viewModelScope, uiState)`.

`grep -rn "started" --include=*.kt app/src/main` (excl `/build/`) returns exactly three code sites — `:26` declaration, `:29` guard, `:35` set — **and nothing anywhere assigns it back to false**. The lifetime is asymmetric: the loop dies with `viewModelScope` (Activity finish → `ViewModel.clear()`), the flag does not.

Failure sequence, all ordinary gestures: back out of the app or swipe it from recents → ViewModel cleared → `while(true)` cancelled → `started` stays `true` → Android keeps the process cached → user reopens → fresh `AppViewModel` → `:163` → guard returns at `:29` → **no now-playing frame ever reaches the watch again for the lifetime of that process**. The tile renders whatever the last frame was, indefinitely.

That is the symptom M9 and M41 describe from the tile side (a frozen "playing" tile), but caused on the phone, where no amount of tile-staleness fixing helps. M9's `isStale` and M41's missing re-render trigger both assume frames stopped arriving because the phone stopped *playing*; here the phone is playing and still not pushing.

**PR #76 does not fix this half.** At `e1576f7`: `private val started = AtomicBoolean(false)` (`:32`), guard `if (!started.compareAndSet(false, true)) return` (`:40`), and the tree's only reset is `started.set(false)` at `:44` — which sits **inside the GooglePlayServices-unavailable early-return block** (`:41-46`), before the `scope.launch` at `:48`. `git show e1576f7:…WearBridge.kt | grep -n "invokeOnCompletion\|fun stop\|set(false)\|compareAndSet"` = 2 hits, both quoted above: no completion handler, no `stop()`. M10's ledger line names "check-then-act" as the defect and reads `status: fixed (PR #76)` — true of the race it names, false of the latch lifetime. Same PARTIAL shape as M9→M41 and L8→M42.

Conf: **h** on the code facts in both trees (both read this shift); **m** on how often the cached process survives long enough for the user to notice (no emulator job exists per M25, so nothing in the repo can demonstrate it).

Cheapest correct patch: `scope.launch(…) { … }.invokeOnCompletion { started.set(false) }` — one line. Honestly noted: it leaves an ordering window, because a new `AppViewModel` created before the old job finishes completing fails the CAS and is then never re-armed. The durable shape is in the Gap Analysis below.

### M71 — an optimistic marker with no failure path

```
239: private fun loadChapters(podcast: PodcastEntity) {
240:     chaptersLoadedFor = podcast.id          // set BEFORE the load
241:     val url = podcast.chaptersUrl
242:     if (url.isNullOrBlank()) { updateState { it.copy(chapters = emptyList()) }; return }
246:     viewModelScope.launch {
247:         val chapters = chaptersCache.getOrPut(url) { repo.fetchChapters(url) }
248:         if (_uiState.value.current?.id == podcast.id) updateState { it.copy(chapters = chapters) }
249:     }
250: }
```

The gate deciding whether to load is `ui/AppViewModel.kt:148` `if (podcast != null && playback.currentMediaId != chaptersLoadedFor) loadChapters(podcast)`. `chaptersLoadedFor` (`:113`, a plain `var`) is written at `:240` **before** the coroutine at `:246` runs, and nothing resets it if the load comes back empty — `data/FeedRepository.kt:57-63` is `withContext(Dispatchers.IO) { runCatching { … }.getOrDefault(emptyList()) }`, so it cannot throw, it returns `emptyList()`.

Consequence: one failed or empty chapter fetch marks the episode loaded forever. Replaying, pausing and resuming that episode never retries (`currentMediaId == chaptersLoadedFor`), and the UI shows no chapters with no reason. Only playing a *different* episode and coming back re-arms it. This compounds M23 (the parser drops every chapter when JSON key order differs from the test fixture) and L23 (feed/parse failures all surface as one generic message): a silently-empty chapter list is indistinguishable from "this episode has no chapters", and is now also unretryable.

Second defect on the same line: `chaptersCache` is a `ConcurrentHashMap` (`:114`) and `getOrPut` is the Kotlin **stdlib extension** — `get(key) ?: defaultValue().also { put(key, it) }`, not `computeIfAbsent`. Because the default lambda is a *suspend* call that leaves the Main thread, two `loadChapters` coroutines for the same `url` can both miss and both fetch. Reachable by fast next/prev across two episodes sharing a `chaptersUrl`; the cost is a second uncapped feed download (M24) whose result is then discarded. The map's type promises atomicity it does not deliver.

Conf **h** on the control flow (every cited line read this shift); the duplicate-fetch half **m** (not reproduced — needs two overlapping loads).
Dedupe, honest: measured against the ledger this shift — `chaptersCache` = 1 prior mention (a seam read, no finding filed on it), `syncMutex` = 4, `thread` = 8, `Volatile` = 3, `Dispatchers.Default` = 0. `chaptersLoadedFor` and `getOrPut` were **not** grepped against the ledger this shift (call budget); the next shift should confirm neither token already carries an ID before treating this entry as first.

## Rich Hickey pass

Thesis this census produced: **the repo annotates visibility but never lifetime.** All 7 concurrency-primitive sites: `PlaybackClient.kt:75` `@Volatile cleanedUp`; `WearBridge.kt:25` `@Volatile started` (+ `AtomicBoolean started` and `@Volatile watchPresent` on PR #76); `AppViewModel.kt:112,114` `AtomicLong`/`ConcurrentHashMap`; `FeedRepository.kt:22` `Mutex`. Two of the three boolean latches (`cleanedUp` = H5, `started` = H10) use exactly the right primitive for cross-thread visibility and still break, because the defect was never visibility — it is that **nothing clears the flag when its owner dies**. A volatile flag is still a process-global mutable carrying an implicit temporal contract; the honest shape makes "is it running" a property of the `Job` that runs, not a boolean a future maintainer must remember to reset. Same complection as M46 (`system/Lifecycle.kt`'s Component pair encoding a temporal contract Hilt already owns) and M63 (`di/MediaModule` declaring a provider nobody consumes): **two owners of one lifetime.** `FeedRepository`'s `Mutex` is the one correct use — it guards a real suspend boundary across threads with no global flag. PR #76's `watchPresent` is also correct: written by a GMS `Task` callback, read by the poll loop, no lifetime attached.

Shape verdicts: `AudioSystem.kt` (83) right size, one owner, idempotent `start()` (`:27`), no finding. `WearBridge.kt` an `object` holding state that belongs to one ViewModel's lifetime — a scope mismatch, and H10 is what that mismatch costs. `MotionDetector` (`AlakeyUI.kt:426-444`) 19 LOC, one job, correct by implicit confinement (VERIFIED-GOOD 4) with nothing in the class saying so. `AppViewModel`'s mutable surface (5 fields) is small and Main-confined; its two primitives are decoration.
