### H8 — R8 strips the signature Gson's TypeToken depends on (release-only, silent)
`data/AppDatabase.kt:41` builds the chapter list type with
`val type = object : com.google.gson.reflect.TypeToken<List<Chapter>>() {}.type`, and Gson resolves it
at runtime through `getClass().getGenericSuperclass()` — which needs the class file's generic
`Signature` attribute to survive shrinking. It does not:

1. `git grep -n "keepattributes\|Signature" e1576f7 -- '*.pro' '*.kts' '*.kt'` = **1 hit**,
   `app/proguard-rules.pro:6` `-keepattributes SourceFile,LineNumberTable`. No `Signature`, no
   `-keep class * extends com.google.gson.reflect.TypeToken`.
2. `app/build.gradle.kts:51` `isMinifyEnabled = true` on release → R8 runs.
3. Gson cannot save it either: `unzip -l` on the local
   `~/.gradle/caches/.../gson/2.10.1/gson-2.10.1.jar` shows META-INF = MANIFEST.MF, maven/pom.xml,
   maven/pom.properties, versions/9/module-info.class — **no `META-INF/proguard/gson.pro`**, so
   2.10.1 contributes no consumer R8 rules.
4. `-keep class com.example.alakey.data.** { *; }` (`:10`) keeps `Chapter`'s members, which is why the
   *field* mapping is fine; it does nothing for the anonymous TypeToken subclass's signature.
5. The failure is **silent by construction**: `:42` `runCatching { gson.fromJson<List<Chapter>>(value, type) }.getOrDefault(emptyList())`
   turns Gson's `IllegalArgumentException: TypeToken must be created with a type argument` into an
   empty chapter list — the exact hazard LEDGER `CONVERTERS-GUARD-NOTE` flagged as shape-only now has
   a payload.

Scoped honestly: `PodcastPalette` is unaffected (`:51` uses the class literal
`PodcastPalette::class.java`, no generic signature involved), and `NetworkLogic.parseItunesResults:17`
is unaffected for the same reason. So the blast radius is **chapters, in signed release builds, only**.

Confidence: config side **h** (every rule read this session); runtime side **m** — no release build was
run this shift (`assembleRelease` needs a keystore the machine does not have, and a build dirties more
tracked `*/build/**` per M28), so this is derived from the rules plus R8/Gson semantics, not observed.

Cheapest fix, and the Hickey one — **delete the reflection magic instead of feeding it rules**:
`gson.fromJson(value, Array<Chapter>::class.java)?.toList() ?: emptyList()`. A `Class` literal for
`Chapter[]` needs no `Signature` attribute, `Chapter` is already kept, and the `?: emptyList()` makes
the null path explicit rather than accidental (CONVERTERS-GUARD-NOTE's durable shape). Belt-and-braces
alternative: add `-keepattributes Signature` plus
`-keep class * extends com.google.gson.reflect.TypeToken` to `app/proguard-rules.pro`. Either way, put
a `Log.w` in the fallback so the next release-only converter failure is not invisible (L13's theme).

### M48 — no CI ever compiles the release variant until a tag exists
`android.yml:29` `./gradlew testDebugUnitTest`, `:32` `assembleDebugAndroidTest`, `:35` `assembleDebug`
— that is the whole verification surface of the `Build & Test` job. `assembleRelease` appears once, at
`:90`, inside the `release` job gated by `:56` `if: startsWith(github.ref, 'refs/tags/v')`. So R8,
the new signing config (`app/build.gradle.kts:32-42`, `wear/build.gradle.kts:27-38`) and the
`mapping.txt` upload (`:102`) are exercised **only on the commit that publishes to users**. PR #76
added 50 lines to this file and made the release path real for the first time (H1) without adding a
gate for it.

Cheap gate that needs no keystore: add `./gradlew :app:minifyReleaseWithR8` to the build job — R8 runs
before packaging/signing, so it compiles the release variant and fails on missing classes or broken
rules on every PR. Honest limit: it would **not** have caught H8 (shrinking a signature is not an R8
error), so it buys rule/compile coverage, not reflection coverage.

### L49 — secret interpolation into `run:` shells
`:78` `if [ -z "${{ secrets.KEYSTORE_BASE64 }}" ]; then` and `:86`
`echo "${{ secrets.KEYSTORE_BASE64 }}" | base64 -d > app/alakey-release.keystore` expand the secret
into the script text before bash sees it, while `:91-95` passes the same values through `env:` — the
correct shape, already in the file three steps later. Base64's alphabet is harmless today, so this is
hygiene, not a live hole: the risk is a `KEYSTORE_PASSWORD` containing `"` or `$(` breaking (or
executing inside) the step, and the pattern being copied by the next contributor. Fix: give both steps
`env: KEYSTORE_BASE64: ${{ secrets.KEYSTORE_BASE64 }}` and use `[ -z "$KEYSTORE_BASE64" ]` /
`printf '%s' "$KEYSTORE_BASE64" | base64 -d`.
